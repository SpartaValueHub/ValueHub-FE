# 채팅 전송 실패 — 원인과 해결

## 한 줄 요약

메시지 **목록(REST)** 은 되고, **보내기(WebSocket)** 만 안 됐다.  
브라우저는 게이트웨이에 JWT를 붙일 수 없어서, Next가 쿠키를 Bearer로 바꿔 대신 붙여 주는 방식으로 고쳤다.

---

## 증상

- 채팅방에 들어가면 예전 메시지는 보인다.
- 입력 후 전송을 눌러도 말풍선이 안 생긴다.
- 콘솔에 아래 오류가 **전송 전부터** 반복된다.

`WebSocket connection to 'wss://api.valuehub.kr/chat-service/ws-chat' failed: HTTP Authentication failed; no valid credentials available`

전송 버튼이 원인인 게 아니다.  
방 입장 순간 소켓이 이미 401이고, 4초마다 재시도한다. 보내기는 연결이 없어서 조용히 실패한다.

---

## 문제 위치

로그인 쿠키(`vh_access_token`)는 **프론트 주소**에만 저장된다.  
예: `localhost:3000`에 띄운 사이트 → 쿠키 주인도 `localhost:3000`.  
`api.valuehub.kr` 것이 아니다.

브라우저 규칙: A 사이트 쿠키를 B 사이트 요청에 안 붙인다.

그래서 **같은 채팅인데 길이 둘**이다.

|                        | 목록 (REST)                           | 보내기 (WebSocket) — 수정 전            |
| ---------------------- | ------------------------------------- | --------------------------------------- |
| 누가 게이트웨이에 가나 | Next 서버                             | **브라우저가 직접**                     |
| 쿠키가 가나            | `localhost:3000`으로 가서 Next가 읽음 | `api.valuehub.kr`이라 쿠키 없음         |
| Authorization 헤더     | 서버가 넣을 수 있음                   | 브라우저 WebSocket은 **헤더를 못 넣음** |
| 결과                   | 200, 이력 보임                        | 401, 전송 불가                          |

상대가 온라인이 아니라서가 아니고, 두 브라우저가 같은 계정이라서가 아니다. **핸드셰이크에 토큰이 없는 것**이 원인이다.

---

## 수정 전 흐름 (실패)

브라우저는 게이트웨이에 직접 붙는다. 쿠키도 Bearer도 없다.

```
브라우저                      게이트웨이
(localhost:3000)              (api.valuehub.kr)
     │                              │
     │  소켓 열기                    │
     │  쿠키 없음 / Authorization 없음
     │─────────────────────────────►│
     │                              │  401
     │  HTTP Authentication failed  │
     │◄─────────────────────────────│
     │                              │
     │  "안녕" 보내기                │
     │  (연결이 없어서 아무 것도 안 감)
```

목록만 되는 이유 (REST는 Next를 거친다):

```
브라우저                  Next                     게이트웨이
(localhost:3000)          (서버)                   (api.valuehub.kr)
     │                      │                           │
     │  GET 메시지 목록      │                           │
     │  + 쿠키 첨부          │                           │
     │─────────────────────►│                           │
     │                      │  쿠키에서 토큰 꺼냄         │
     │                      │  게이트웨이로 REST 호출     │
     │                      │──────────────────────────►│
     │                      │                           │  통과
     │  예전 메시지 표시     │◄──────────────────────────│
     │◄─────────────────────│                           │
```

---

## 해결

브라우저가 게이트웨이에 직접 가지 않는다.  
**지금 보고 있는 사이트(Next)** 로 소켓을 열고, Next가 쿠키를 `Authorization: Bearer`로 바꿔 게이트웨이에 업그레이드한다.

서버가 브라우저에 주는 값은 호스트가 아니라 경로만이다.

- `wsUrl`: `/api/chat/ws-chat`
- 호스트는 `localhost:3000`으로 고정하지 않는다.
- 브라우저가 **현재 페이지 주소**를 앞에 붙인다.

| 내가 연 페이지                      | 브라우저가 여는 소켓                      |
| ----------------------------------- | ----------------------------------------- |
| `http://localhost:3000/chat/...`    | `ws://localhost:3000/api/chat/ws-chat`    |
| `http://192.168.x.x:3000/chat/...`  | `ws://192.168.x.x:3000/api/chat/ws-chat`  |
| `https://www.valuehub.art/chat/...` | `wss://www.valuehub.art/api/chat/ws-chat` |

채팅 서버가 localhost로 바뀐 게 아니다.  
실제 저장·방송은 여전히 게이트웨이(`CHAT_API_URL`)다.  
브라우저가 보는 소켓 주소만 Next 주소다. 쿠키 주인과 소켓 주인을 같게 하려는 것이다.

---

## 수정 후 흐름 (성공)

```
브라우저                  Next                     게이트웨이
(localhost:3000)          (서버)                   (api.valuehub.kr)
     │                      │                           │
     │  소켓 열기            │                           │
     │  + 쿠키 첨부          │                           │
     │─────────────────────►│                           │
     │                      │  쿠키에서 토큰 꺼냄         │
     │                      │  Authorization: Bearer …  │
     │                      │──────────────────────────►│
     │                      │                           │  통과
     │  연결됨               │◄──────────────────────────│
     │◄─────────────────────│                           │
     │                      │                           │
     │  "안녕" 보내기        │  그대로 전달               │
     │─────────────────────►│──────────────────────────►│
```

비유: 백엔드 건물에는 출입증이 필요한데, 브라우저가 들고 있는 건 **프론트 건물 출입증**이다.  
그래서 프론트를 한 번 거쳐, 거기서 확인한 뒤 백엔드로 데려다 준다.

---

## 손댄 코드 (프론트)

- `app/api/chat/stomp/route.ts` — 브라우저에 `/api/chat/ws-chat`만 내려줌
- `hooks/chat/useChatRoomSocket.ts` — 현재 페이지 출처로 소켓 연결
- `lib/chat/ws-proxy.ts` + `instrumentation.ts` — Next가 쿠키 → Bearer로 게이트웨이 업그레이드

---

## 확인 방법

1. `pnpm dev`를 **재시작**한다. (`instrumentation.ts`는 서버 기동 때 로드된다)
2. 채팅방을 연다.
3. DevTools → Network → WS 주소가 `api.valuehub.kr`이 아니라 `localhost:3000/api/chat/ws-chat`인지 본다.
4. 메시지를 보낸다. 말풍선은 서버 echo가 온 뒤에 생긴다.

---

## 참고

- 이 프록시는 `pnpm dev` / `next start`처럼 Node 서버가 떠 있을 때 동작한다.
- Vercel 서버리스에서는 WebSocket 업그레이드 프록시가 어려울 수 있다. 그때는 게이트웨이가 쿼리 `accessToken`을 받는 방식(SSE와 같은 패턴)이 필요하다.
